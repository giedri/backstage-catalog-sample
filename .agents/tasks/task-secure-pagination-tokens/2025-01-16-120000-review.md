# HMAC-signed pagination tokens replacing insecure base64 encoding

This change replaces the insecure plain base64-encoded DynamoDB `LastEvaluatedKey` pagination tokens with HMAC-SHA256 signed, customer-bound tokens. The new `pagination.py` utility signs tokens using a shared secret (`PAGINATION_SECRET` env var), embeds the `customer_id` in the signed payload so tokens cannot be replayed across partitions, and verifies signatures with constant-time comparison on decode. The service layer (`order_service.py`) was updated to call the new utility, and the handler's existing `ValueError` catch path handles the new `InvalidPaginationTokenError` subclass without modification.

**Watch for:** The token payload is signed but not encrypted — DynamoDB key structure (table key names, partition scheme) is readable by anyone who base64-decodes the token (confirmed). The `template.yaml` default secret is the literal string `change-me-in-production`, which will silently deploy as a valid (but weak) HMAC key if the parameter isn't overridden (confirmed). There is no token expiration mechanism, so a captured token remains valid indefinitely until the secret rotates (confirmed).

## High-level view

The pagination utility uses a straightforward sign-then-verify pattern: the DynamoDB key and customer ID are JSON-serialized, base64url-encoded, then HMAC-SHA256 signed with a secret from the environment. Context binding is enforced by including `customer_id` in the signed payload and comparing it at decode time, which blocks cross-partition replay even if an attacker intercepts a valid token.

The secret lifecycle relies entirely on the `PAGINATION_SECRET` CloudFormation parameter. There's no secret rotation story — rotating the secret immediately invalidates all outstanding pagination tokens, which is acceptable (pagination is ephemeral) but should be understood operationally.

The payload is integrity-protected but readable. An attacker can decode the base64url payload and learn the DynamoDB key attribute names (`pk`, `sk`, `gsi1pk`, `gsi1sk`) and their naming convention. This is informational leakage rather than a functional vulnerability, but it does expose internal schema to API consumers.

<summary>Issues (4)</summary>

1. **Unused import** — `InvalidPaginationTokenError` is imported in `order_service.py` but never referenced. Remove it or add an explicit catch for clearer intent.
2. **Payload confidentiality** — Token payloads are signed but not encrypted; DynamoDB key schema and naming conventions are visible to any API consumer who base64-decodes the first segment. Consider encrypting the payload (AES-GCM with the same secret) if schema exposure matters.
3. **Weak default secret** — The `PaginationSecret` CloudFormation parameter defaults to `change-me-in-production`. A deployment that omits the override will operate with a publicly-known HMAC key, silently voiding the security guarantee. Consider removing the default or adding a `MinLength` constraint.
4. **No token TTL** — Tokens have no expiration. A leaked token for a given customer remains usable until the HMAC secret rotates. For pagination tokens (short-lived by nature), this is low severity, but adding a timestamp to the signed payload with a 15-minute window would eliminate the risk entirely.

## Schema leakage via unencrypted payload

The token format is `base64url(json_payload).base64url(hmac_signature)`. Anyone with access to a pagination token can decode the first segment and see:

```json
{"customer_id":"CUST-001","key":{"pk":"ORDER#ORD-123","sk":"ORDER#ORD-123","gsi1pk":"CUSTOMER#CUST-001","gsi1sk":"2024-01-15T10:30:00Z"}}
```

This reveals the DynamoDB key naming convention (`pk`/`sk`/`gsi1pk`/`gsi1sk`), the key value format (`ORDER#`, `CUSTOMER#`), and the sort key structure (ISO timestamps). For a public-facing API, encrypting the payload before signing (encrypt-then-MAC) would close this gap.

## Default secret in template.yaml

The `PaginationSecret` parameter has `Default: change-me-in-production`. CloudFormation will happily deploy with this value. Since the HMAC security guarantee depends entirely on the secret being unknown to attackers, any deployment that forgets to override this parameter operates with no effective token protection. The `NoEcho: true` prevents the value from appearing in CloudFormation console output, but doesn't prevent the weak default from being used.

Removing the `Default` field entirely would force an explicit value at deploy time — a hard failure is safer than a silent misconfiguration.

## Unused import and error path asymmetry

`InvalidPaginationTokenError` is imported in `order_service.py` but never referenced in a `try/except` or any other statement. The error propagates correctly through the handler's `ValueError` catch without it. However, this means invalid pagination tokens and other `ValueError` sources (e.g., `int(params.get("limit"))` in the handler) are indistinguishable in error responses. If the service layer should differentiate token errors from other validation errors in the future, the import should be used in an explicit catch; otherwise it's dead code that should be removed.

## Test coverage gaps

Not tested: the integration path through `order_service.list_orders` with the new signing (the existing `test_list_orders_pagination` covers this but requires moto and couldn't be run in this sandbox). Not tested: behavior when `PAGINATION_SECRET` is missing (the `RuntimeError` path). Not tested: extremely large DynamoDB keys that might exceed URL length limits when base64url-encoded and passed as query parameters.
