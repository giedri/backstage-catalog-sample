# Order status state machine and optimistic concurrency

This change closes the state-manipulation vulnerability in `PATCH /v1/orders/{orderId}/status` by adding a server-side state machine. A `VALID_TRANSITIONS` map in the model layer defines which status moves are legal (forward-only plus cancellation from PENDING/CONFIRMED). The service layer fetches the current order, validates the requested transition against the map, and writes back with a DynamoDB `ConditionExpression` that asserts the status hasn't changed since the read. The handler now captures the admin's `sub` claim and passes it as an `actor` for audit logging. Invalid transitions surface as 409 CONFLICT.

**Watch for:** The race window between the `get_order` read and the conditional `update_item` write means a concurrent modifier sees `OrderConflictError` but the handler has no `except` clause for it, so it falls through to the generic 500 path (confirmed). The `actor` parameter is typed `str | None` with a default of `None`, which means a direct service-layer call without an actor still succeeds and logs "unknown" — fine for tests, but a latent gap if other internal callers are added later (likely).

## High-level view

The state machine is a dict of `OrderStatus -> set[OrderStatus]` with terminal states mapped to empty sets. The separation between model (defines transitions), service (enforces them), and handler (maps errors to HTTP) follows the project's existing layering.

Optimistic concurrency is implemented by conditioning the DynamoDB write on `order_status = :expected_status`. This prevents two concurrent admins from both reading PENDING and both writing CONFIRMED, but it surfaces as an `OrderConflictError` that the handler doesn't catch — resulting in a 500 rather than a retriable 409.

Test coverage exercises every edge of the state machine graph (5 valid, 6 invalid), but there are no tests for the optimistic-concurrency conflict path.

## Unhandled `OrderConflictError` on concurrent writes

The service previously raised `OrderNotFoundError` when the `ConditionExpression` failed (it only checked `attribute_exists(pk)`). Now the condition also asserts `order_status = :expected_status`, and a failure raises `OrderConflictError` instead. The handler imports `OrderNotFoundError` and catches it, but `OrderConflictError` is neither imported nor caught:

```python
# update_order_status.py — current exception handlers
except AuthError as e:
    return error(e.code, e.message, 401 if e.code == "UNAUTHORIZED" else 403)
except InvalidTransitionError as e:
    return error("CONFLICT", str(e), 409)
except OrderNotFoundError:
    return error("NOT_FOUND", "Order not found", 404)
```

If two admins hit the endpoint simultaneously for the same order, the loser gets a 500 Internal Server Error instead of a meaningful 409 that signals "retry". The read-then-write window is not atomic, but the optimistic concurrency guard preserves data integrity — the only gap is the handler's error mapping. The fix is a two-line addition: `except OrderConflictError as e: return error("CONFLICT", str(e), 409)`.

## Actor identity gap

The `actor` parameter defaults to `None` and the log line falls back to `"unknown"`. If the service is ever invoked from an internal event bus or step function without an actor, the audit trail loses its value. Making `actor` required (or logging at WARNING when absent) would surface the gap early rather than silently degrading.

## Test coverage gaps

What's missing is a test that exercises the optimistic-concurrency conflict path — a scenario where the DynamoDB condition fails because another write landed between the read and the update. This is the one production failure mode introduced by this change that has no coverage.
