# JWT authorization and IDOR fix for order endpoints

This change adds authentication and object-level authorization to the order management API to close a HIGH-severity IDOR vulnerability. The approach layers a JWT authorizer on the API Gateway HttpApi (rejecting unauthenticated requests at the edge) and adds per-handler authorization logic that compares the `customer_id` claim from the token against the resource being accessed. The health endpoint is explicitly excluded from authentication. Two new SAM parameters (`JwtIssuer`, `JwtAudience`) allow deploy-time configuration of the identity provider.

**Watch for:** The `get_order` and `update_order_status` handlers return 404 for non-existent orders before reaching the authorization check, leaking order existence to any authenticated user (confirmed). The `create_order` handler skips authorization entirely when the JWT claims are absent—but in production the gateway rejects those requests, so this only matters if the Lambda is invoked directly or the authorizer is misconfigured (likely). No `sub` claim mapping exists; the system assumes the IdP issues a custom `customer_id` claim, which is non-standard and fragile (confirmed).

## High-level view

The gateway-level defense is sound: an explicit `OrderApi` HttpApi resource wires a JWT authorizer as `DefaultAuthorizer`, covering all routes except `/health` which opts out with `Authorizer: NONE`. All function events reference `ApiId: !Ref OrderApi`, binding them to the authenticated API. The authorizer uses deploy-time parameters, so no secrets are committed.

Handler-level authorization is consistent across all four order endpoints. A shared `authorize_customer_access(event, customer_id)` utility extracts the `customer_id` claim from the HTTP API v2 JWT authorizer location and compares it to the resource owner. On mismatch or missing claims the handler returns 403 FORBIDDEN. The design correctly fails closed.

The `get_order` and `update_order_status` handlers must fetch the order from DynamoDB before they can authorize, since the resource owner isn't in the URL. This creates an information leak: a 404 response tells an attacker that an order ID doesn't exist, while a 403 confirms it does.  A uniform 403 for both missing and unauthorized would close this.

The implementation relies on a custom `customer_id` JWT claim. Standard OIDC tokens carry `sub` but not `customer_id`. If the IdP doesn't issue this claim, every request fails authorization silently (the utility returns `None` and denies access). There's no documentation or validation that flags this configuration requirement.

Test coverage is thorough for the authorization paths: every handler has explicit 403-on-mismatch and 403-on-missing-claims tests. The auth utility itself has edge-case coverage for malformed events. Tests could not be executed in this environment but are structurally sound.

<details>
<summary>Issues (4)</summary>

1. **Order existence leak via 404 vs 403** — `get_order` and `update_order_status` return 404 for missing orders before checking authorization, letting any authenticated user probe which order IDs exist. Return a uniform 403 (or 404 for both cases) when the caller isn't the owner.
2. **Custom claim dependency undocumented** — The system requires a `customer_id` claim in the JWT, which isn't a standard OIDC claim. Add documentation or a SAM parameter/output noting this requirement so operators know what claim the IdP must include.
3. **Double fetch in update_order_status** — The handler calls `service.get_order(order_id)` for authorization, then calls `service.update_order_status(order_id, new_status)` which internally fetches the order again. This is a wasted DynamoDB read; pass the already-fetched order to the update path or use a conditional update.
4. **No authorization scope enforcement** — `AuthorizationScopes` is set to an empty list, meaning any valid JWT is accepted regardless of scopes. If the IdP issues scoped tokens, this should be tightened to require an appropriate scope (e.g., `orders:read`, `orders:write`).

## Order existence oracle in get/update handlers

Both `get_order` and `update_order_status` follow the same pattern: fetch the order, then check authorization. If the order doesn't exist, `OrderNotFoundError` propagates to the `except` clause and returns 404 before any authorization logic runs.

```python
# get_order.py
order = service.get_order(order_id)          # raises OrderNotFoundError → 404
is_authorized, _ = authorize_customer_access(event, order.customer_id)  # never reached
```

An authenticated attacker can enumerate order IDs: 404 means "doesn't exist", 403 means "exists but belongs to someone else." The fix is to return the same status code for both cases (either always 403, or always 404 when the caller isn't the owner). The principle: an unauthorized user should learn nothing about resources they don't own.

## Reliance on non-standard `customer_id` claim

The `get_customer_id_from_event` function expects `claims["customer_id"]`. Standard OIDC tokens provide `sub` (subject identifier), and Cognito adds `cognito:username` or custom attributes prefixed with `custom:`. If an operator deploys this stack with a standard Cognito user pool and doesn't add a custom claim mapping, every request will be denied because `customer_id` resolves to `None`.

The fail-closed behavior is correct from a security standpoint (deny by default), but operational failures will be silent: 403s with no clear indication that the claim name is wrong. A startup-time check (e.g., environment variable naming the expected claim) or at minimum a README note would prevent hours of debugging.

## Double DynamoDB read in update_order_status

```python
order = service.get_order(order_id)              # read #1 (for auth)
# ... authorization check ...
order = service.update_order_status(order_id, new_status)  # read #2 internally
```

The `update_order_status` service method almost certainly fetches the order again to validate the state transition. For a low-traffic service this is negligible, but it's a pattern that doubles read costs for every status update. A conditional DynamoDB update expression that checks `customer_id` in the same operation would be both more efficient and more correct (no TOCTOU race between the read and the write).

## Empty authorization scopes

The JWT authorizer is configured with `AuthorizationScopes: []`. This means API Gateway validates the token signature and expiry but does not check the `scope` or `scp` claim. Any valid token from the same issuer—including tokens intended for other services—will pass the gateway check. If this service shares an IdP with other APIs, a token minted for a different audience/purpose could access order endpoints as long as it carries the right `customer_id` claim.

The `audience` parameter provides some protection (the token's `aud` must match), but scopes would add defense-in-depth. This is low severity if the IdP issues dedicated tokens for this service, but worth noting.

## Test coverage

The test suite covers:
- Successful operations with valid claims
- 403 on customer_id mismatch for all four handlers
- 403 on missing claims (list_orders explicitly, others implicitly through the auth utility tests)
- Auth utility edge cases: missing authorizer, missing jwt key, missing claims key, empty claim, None requestContext

Not tested: the 404-before-403 ordering issue (ironically, the `test_update_order_status_not_found` test sends claims for `CUST-001` and gets a 404 for a non-existent order, demonstrating the leak). Also not tested: behavior when `customer_id` claim is a non-string type (integer, list), which `claims.get("customer_id")` would return truthy, pass the `if not customer_id` check, and then fail the string comparison. This is an edge case but worth a defensive `str()` cast or type check.
